>

> 有完整排列监督时结论有可能翻转。论文的问题是**没做这个对照**，而不是**被证明错误**。
>
> 想接着做的人，该跑的实验是：用一个能塞进显存的 teacher 做排列蒸馏，
> 让 N×K 矩阵的每一列都有信号，再重测 `llm_rerank.py` 里的匈牙利 vs argsort。


对 **hLLM: Single Pass Decoding for Generative Reranking**（arXiv [2609.01807](https://arxiv.org/abs/2609.01807)，Meta，2026-09-01）的复现与验证。

论文把生成式重排序表述为组合优化问题：LLM 的输出只需是 N 个序号构成的排列，因此不必自回归逐 token 解码。方法是在 prefill 隐状态上挂一个轻量打分头，读出 N×K 的物品-位置矩阵，再用匈牙利算法解成最优二部图匹配。论文报告 28 ms 端到端、相对自回归 64× 加速、质量与 teacher 持平。

## 复现范围

硬件是 RTX 4070（12 GB）+ 24 核 CPU。**不复现**的部分：

- Amazon Beauty 上的 32B teacher —— 4bit 量化也要约 20 GB，放不下。因此没有教师蒸馏，
  训练信号改用真实点击标签（论文自己的 training signal 消融里就含无蒸馏这一维）
- 论文的内部数据集（未公开）
- 论文报告的 28 ms 绝对延迟（取决于其服务器 GPU；本机同样的一次前向是 71–81 ms）

**复现的是解码器**——论文的实际贡献所在。E1–E5 在 CPU 上剖析解码机制本身，
E6 在真实的 Qwen3-0.6B + Amazon Beauty 上做同源对比。

```sh
python -m venv .venv
.venv/bin/pip install -r requirements.txt

cd hllm
./run_all.sh                    # E1-E5, CPU only, ~20 min

# E6 needs a CUDA GPU (~5 GB) and the Amazon Beauty dump:
mkdir -p data && cd data
base=https://huggingface.co/datasets/milistu/Amazon_Beauty_2014/resolve/main/5_core
curl -L -o reviews_5core.parquet  $base/reviews.parquet
curl -L -o metadata_5core.parquet $base/metadata.parquet
cd ..
../.venv/bin/python prep_data.py     # build slates
./run_llm.sh                         # ~95 min on an RTX 4070
```

所有输出在 `results/`。`data/` 里的中间产物（约 474 MB）不入库，由上面的脚本重建。

## 结论

### 站得住的部分

**求解器开销的量级是真的。** 论文报 N=50 时 LAPJV 花 0.008 ms。用专用 C++ 实现实测 0.0149 ms，差 1.9 倍，在硬件差异范围内——论文这个数字可信。（注意 SciPy 的 `linear_sum_assignment` 慢 2.5 倍，用它测会得出论文虚报的错误印象。）

```
N=50 求解耗时  scipy_mJV 0.0374    lap_JV 0.0173    lapjv_cpp 0.0149    论文 0.008
```

**合法排列的构造性保证是真的**，这是指派问题的定义性质，E5 在每次调用中断言了输出的合法性。

**审稿意见担心的 top-K / 可变 N 不是障碍。** 矩形指派原生支持，复杂度 O(N·K·min(N,K))，比论文一直在解的全排列**便宜 17～1295 倍**：

```
N=1000:  K=10 → 0.0228 ms      K=N → 29.59 ms      差 1295 倍
```

论文确实没写这一节，但那是文档缺失，不是方法缺陷。

### 不成立或被夸大的部分

**64× 这个加速比的分母有问题。** 论文自己的主结果表里：

| | 延迟 | AUC | NDCG@1 |
|---|---|---|---|
| Teacher（带 reasoning trace） | 1807 ms | 0.5911 | 0.1776 |
| Teacher（不带） | **88 ms** | 0.5912 | 0.1779 |
| hLLM | 28 ms | 0.5907 | 0.1791 |

reasoning trace 让延迟涨 20 倍、质量分毫未动。论文拿这个被自己数据证伪的配置当分母算出 1807/28 = 64×。**对齐质量后的真实加速是 88/28 ≈ 3.1×。**

**"求解器占比 <0.03%" 只在 N=50 成立。** 论文自己的内部数据集最大 slate 是 150：

```
最快实现占 28 ms 的比例:  N=50 → 0.053%   N=150 → 0.537%   N=500 → 10.2%   N=1000 → 48.3%
```

定性结论（可忽略）在论文的实验设定内没错，但这个数字不该被外推——全排列解码在 N≥500 时求解器会变成主要成本。（若改用 top-K 解码则不受影响，见 E5。）

### 论文没讨论的结构性问题

**如果打分矩阵可分解，匈牙利算法就是排序的昂贵写法。** 当 M 是秩 1 的（`M_ij = s_i · w_j`，物品质量 × 位置价值，w 单调递减），重排不等式保证最优指派恰好等于按 `s` 降序排列。E2 在 300 次试验中验证：

```
eps=0.00   kendall_tau 1.0000   exact_match 100.0%
```

`eps` 是叠加在秩 1 结构上的交互噪声。eps=0 时两个解码器逐位相同——此时 O(N³) 的求解器在做 O(N log N) 的事。论文的框架只有在矩阵携带真实的物品-位置交互时才有内容，而论文从未测量学到的矩阵有多少交互成分。

**打分头若逐物品独立打分，求解器的输出不含任何排序信息。** 论文的 Linear Probe 变体是 "each item scored independently"。这种头产生的 M 没有列方向变化，于是**所有 N! 个排列的指派目标值完全相同**：

```
Hungarian 目标值 vs 随机排列目标值，最大差距: 0.00e+00
```

匈牙利算法此时返回的是求解器内部顺序决定的任意排列。论文的消融显示 Linear Probe 表现差，但归因于容量不足（Sec 6.1 的 "capacity gap"）——真实原因是结构性的：这个组合根本无法编码排序。

**最优指派对矩阵噪声不稳健。** E3 在「秩 1 信号 + iid 单元噪声」上扫描噪声水平：

```
sigma    NDCG@10 (匈牙利 / argsort)     R@1 (匈牙利 / argsort)    解码结果相同
 0.00      0.3754 / 0.3754              0.1700 / 0.1700            100.0%
 0.10      0.3099 / 0.3766              0.0990 / 0.1730              0.0%
 0.50      0.2051 / 0.3762              0.0415 / 0.1790              0.0%
```

匈牙利最大化 `Σ M[i, pos(i)]`，会去榨取单元级噪声；按行聚合再排序则把噪声平均掉。σ=0.5 时匈牙利的 R@1 只有 argsort 的 1/4。

这个实验有个明确的局限：矩阵是合成的，不是训练出来的。论文的打分头是**与匈牙利解码联合训练**的，会自动学到适配该解码器的矩阵结构。E4 用端到端训练补上这一点。

### E4：论文缺失的那个消融

hLLM 同时改了两件事——打分头输出 N×K 矩阵，解码器换成匈牙利算法。论文只报告两者合起来的效果，从未分离。这意味着它在 Amazon Beauty 上的增益（同为 0.6B 规模，AUC 0.5122 → 0.6168）无法归因：可能来自蒸馏、来自 LoRA、来自注意力头，也可能来自组合优化框架本身。

E4 用共享的 encoder 架构、相同数据、相同训练预算训练两个头，然后把矩阵头用四种方式解码。物品相关性依赖于它所在的 slate（`rel = x·w + 0.8·contrast + noise`），因此无上下文的打分器无法解决——这正是重排序的定义。

3 个随机种子，N=20，8000 训练 / 2000 测试 slate，20 epoch，relevance noise 1.5：

| 配置 | NDCG@10 | R@1 | 解码 ms |
|---|---|---|---|
| A 标量头 + argsort | 0.9391 ± 0.0152 | 0.5792 ± 0.0663 | 0.0002 |
| **B 矩阵头 + 匈牙利**（hLLM） | **0.9469 ± 0.0135** | **0.6267 ± 0.0571** | 0.0073 |
| C 矩阵头 + 行均值排序 | 0.4503 ± 0.0168 | 0.0003 ± 0.0005 | 0.0006 |
| D 矩阵头 + 首列排序 | 0.9015 ± 0.0172 | 0.6253 ± 0.0556 | 0.0002 |
| E 矩阵头 + 贪心解码 | 0.9413 ± 0.0120 | 0.6253 ± 0.0556 | 0.0298 |

种子级标准差大于配置间差距，所以按 slate 配对比较（所有配置排的是同一批测试 slate，6000 个配对样本）：

```
B - A: delta +0.0078  [95% CI +0.0071, +0.0085]  t= 21.23  p=1.6e-96
B - E: delta +0.0056  [95% CI +0.0050, +0.0062]  t= 18.01  p=1.2e-70
B - D: delta +0.0454  [95% CI +0.0439, +0.0469]  t= 59.21  p<1e-300
B - C: delta +0.4967  [95% CI +0.4935, +0.4998]  t=306.07  p<1e-300
```

**结论一：组合优化框架的增益是真的，但很小。** 匈牙利解码显著优于标量头 + 排序（p=1.6e-96），但效应量是 +0.0078 NDCG@10，相对提升 0.83%。代价是解码延迟 37 倍（0.0002 → 0.0073 ms）和 N 倍大的输出头。论文的方向没错，量级值得重新表述。

**结论二：增益基本不来自「最优性」。** 贪心解码（逐位置取未用过的最高分，同样是合法排列，不需要 repair）拿到了其中 93%——B 相对 E 只多 +0.0056，尽管两者在 **0.0%** 的 slate 上解出相同排列。论文强调 "a valid permutation by construction rather than by repair" 的优势，在质量上主要来自「有一个 N×K 矩阵可读」，而非「解出了那个矩阵的最优指派」。

**结论三：矩阵的读出方式是关键，且不可互换。** 用 Sinkhorn 排列目标训练出的矩阵，行均值读出会彻底崩溃（NDCG 0.45，R@1 ≈ 0）。这也说明 E3 里「行聚合更稳健」的结论不能外推到端到端训练的矩阵上——头会学到适配其解码器的结构。

**结论四：方向随任务难度翻转。** 把 relevance noise 降到 0.1（近乎无噪、可完美求解）后 NDCG@10 全部撞上天花板（A 0.9996 / B 0.9994），配对差变成 `B - A = -0.0002`（p=0.02）——标量头反而略优。同一设定下 `B - E = +0.0214`，最优指派对贪心的优势比困难任务上更大。任何单一难度下的结论都不该外推。完整输出见 `results/e4_easy.txt`。


### E6：真实 LLM 上的同源对比

数据是 Amazon Beauty 2014 五核（9386 训练 / 494 评测 slate，50 候选，每 slate 一个正例）。
slate 结构是从论文自己的数字反推的：它报告的 NDCG@1 与 Recall@1 数值完全相同，
这只在单正例时成立。

三次训练共用 Qwen3-0.6B、同一 LoRA 配置（4.59 M 可训练）、同一批数据、
同一监督信号（gold 属于第 1 位）。差异只在输出头、训练损失和解码器：

| 配置 | R@1 | R@10 | NDCG@10 | 延迟中位数 | 合法排列 |
|---|---|---|---|---|---|
| 自回归解码（逐 token 生成序号） | 0.2126 | 0.4170 | 0.2936 | 1568.5 ms | **2.6%** |
| hLLM(CE) + 匈牙利 | **0.2874** | 0.4413 | 0.3465 | 80.8 ms | 100% |
| hLLM(CE) + argsort（同矩阵，无求解器） | 0.2854 | **0.6457** | **0.4531** | 80.7 ms | 100% |
| hLLM(Sinkhorn) + 匈牙利 | 0.2814 | 0.3927 | 0.3240 | 71.3 ms | 100% |
| hLLM(Sinkhorn) + argsort | 0.2854 | 0.6417 | 0.4502 | 71.2 ms | 100% |

**一次前向解码的加速与质量，证实。** 1568.5 → 80.8 ms 是 **19.4×**，而且 hLLM 的 R@1
反而更高（0.2874 vs 0.2126）。论文"O(1) 次前向 + 质量不降"的核心主张，在同骨干同数据
同监督的条件下成立。倍数不是论文的 64×，但方向和量级都对。

**合法排列的必要性，强力证实。** 自回归解码只有 **2.6%** 的输出是合法的 10 项排列，
其余 97.4% 有重复或越界，必须靠 repair 补全。hLLM 恒为 100%。这是论文"by construction
rather than by repair"最有力的一条，也是本次复现中论文站得最稳的主张。
（需注明：我们的自回归基线只监督了第一个序号，没有完整排列的训练目标，
所以 2.6% 里有一部分是训练信号造成的，不纯是自回归解码的固有缺陷。）

**但匈牙利指派本身是负担，不是优势。** 同一个训练好的矩阵，只换解码器：argsort 的
R@10 高 46%（0.6457 vs 0.4413）、NDCG@10 高 31%（0.4531 vs 0.3465），R@1 持平，
延迟一样。原因是单正例监督只训练了矩阵的第 0 列，位置 1–9 那几列没有信号；
匈牙利要用全部 10 列求最优指派，被无监督的噪声列拖累，argsort 只读有监督的那一列。
这正是 CPU 实验 E3 的预测。

**论文的 Sinkhorn 松弛没有救回这一点。** 换成论文的训练信号后匈牙利反而更低
（R@10 0.3927 vs CE 的 0.4413），argsort 则纹丝不动（0.6417 vs 0.6457）。

合起来指向一个解释：**hLLM 真正有效的部分是「一次前向读出矩阵」，而不是「解出该矩阵的
最优指派」。** 而要让所有 K 列都携带信号、让组合优化有意义，必须有完整排列的监督——
那只能来自 teacher 蒸馏，也就是论文用 32B 做的事。论文把这两件事捆在一起报告，
掩盖了后者其实依赖前者。

#### 一个诊断记录

hLLM 最初怎么调都停在随机水平。与其盲调超参，先问「冻结的表示里有没有信息」：
一个 1025 参数的线性探针在**完全冻结**的 hidden states 上拿到 R@1 = 0.148 / R@10 = 0.524，
立刻说明问题在训练/评测代码而非表示层。随后定位到两个自身 bug：

- 矩形 N×K 指派中 `linear_sum_assignment` 返回的 `rows` 是被选中的物品索引，不是 `0..N-1`。
  丢掉它就等于输出位置索引而非物品编号，R@10 恰好卡在 10/50 的随机值。
- batch=1 的梯度噪声让 CE 训练发散（loss 高于 log 50）。加梯度累积后收敛。

顺带得到一个与论文相关的结果：4.73 M 参数的注意力探针峰值 R@1 = 0.150，
和 1 K 参数的线性探针（0.148）几乎相同，之后严重过拟合。论文强调的
Self-Attention head（"each item attends to all others"）在单正例监督下没有体现出优势。

## 汇总

| 论文主张 | 判定 |
|---|---|
| 匈牙利求解在 N=50 只花 0.008 ms | **证实**（专用 LAPJV 实测 0.0149 ms，硬件差异内） |
| 求解器占端到端延迟 <0.03% | **仅在 N=50 成立**；论文自己的 N=150 是 0.54%，全排列 N≥500 时不再可忽略 |
| 构造性保证合法排列 | **证实**（指派问题的定义性质） |
| 相对自回归解码 64× 加速 | **不成立**：论文自己的表格里，去掉 reasoning trace 的 teacher 是 88 ms 且质量不变，真实加速 3.1× |
| 排序质量与 teacher 持平 | 无法验证（32B teacher 放不下） |
| 一次前向解码相对自回归的加速 | **证实**：真实 LLM 上 19.4×（1568.5 → 80.8 ms），且质量不降反升 |
| 合法排列由构造保证（而非 repair） | **强力证实**：自回归解码合法率仅 2.6%，hLLM 恒为 100% |
| 组合优化框架带来质量增益 | **不成立**：同一矩阵换 argsort 解码，R@10 高 46%、NDCG@10 高 31%，延迟相同 |
| Sinkhorn 松弛作为训练信号有效 | **未证实**：换用后匈牙利解码反而更差，argsort 不变 |

审稿意见里，「匈牙利 O(N³) 开销未说明」和「无数据集/指标」两条打空了（论文 5.5 节和第 5 章都写了）；「缺非 LLM 基线」「可变 N / top-K」两条属实但后者技术上不是障碍。审稿人未指出的两个真问题是 **64× 的分母** 和 **缺失的同源消融**。

## 本复现的局限

- **不是论文的实验**。E4 用的是合成重排序任务和 ~100K 参数的 encoder，不是 Amazon Beauty 上的 0.6B LLM。结论说的是「组合优化解码这个机制本身能带来多少」，不是「hLLM 在推荐数据上的表现」。
- E4 的结论对任务难度敏感：噪声 1.5 时匈牙利略优，噪声 0.1 时标量头略优。单一设定的结论不该外推。
- **没有教师蒸馏**，这是与论文最大的偏离。E6 的核心结论（匈牙利不如 argsort）恰恰
  可能被完整排列监督翻转——但那需要 32B teacher，本机放不下。这条结论应读作
  「在单正例真值监督下」，而非无条件成立。
- E6 的自回归基线只监督第一个序号，所以它的 R@10/NDCG@10 和 2.6% 合法率都对它不利；
  R@1 与延迟是公平的对比项。
- 论文报告的 28 ms 依赖其服务器 GPU；本机 4070 上同样的一次前向是 71–81 ms。
  加速比（19.4×）是同机对比，绝对值不可跨硬件比较。
- 教师质量、内部数据集均不可得，论文的主结果表无法独立验证，只能做内部一致性检查（64× 那一条就是这样发现的）。
